# The game server and the test client

`engine/api` puts the engine (`engine/core`) on the network, and `frontend/` is the minimal client that plays through it. Neither decides anything about the game. The server stores games, checks who may answer, and translates; the client renders and clicks. Every rule, sentence, label and number a player sees comes from the engine: views (`engine.view`), redacted events (`engine.eventsFor`), `EventDescriber`, `ActionDescriber`, `DecisionDescriber`, `AttackDamage`, `Costs`.

The contract is `specs/phase-2-engine.md` §12 (REST) and §13 (protocol, DTOs, sessions); `specs/phase-2-examples.md` shows real payloads. Read §13.4 before changing sessions.

## The layers

```
controller ──▶ domain ◀── adapter ──▶ dao
```

| Layer | Holds | Knows |
|---|---|---|
| `controller` | The endpoints: `rest/` (controllers, `dto/`), `ws/` (handshake, handler, `GameSocketRegistry`, `SeatSocket`, `message/`), `mappers/` (DTOs and messages ↔ business objects, the protocol JSON) | the domain only |
| `domain` | `bo/` (business objects: `game`, `view`, `command`, `error`, `evaluation`), `services/` (`game`, `update`, `bot`, `security`, `content`, `evaluation`), `mappers/view` (engine → what a seat may see), `ports/` (the interfaces it needs) | nothing but itself and core; no transport, no JSON |
| `adapter` | The ports implemented on the DAOs (`game/GameSessionAdapter`, `notification/GameNotificationAdapter`, `evaluation/EvaluationAdapter`, `art/CardArtAdapter`), and the entity ↔ business object mapping (`mappers/game`) | the domain and the DAOs |
| `dao` | Pure data: `entities/`, `game/GameDao`, `notification/GameNotificationDao`, `evaluation/EvaluationDao`, `art/CardArtDao`, with an `*InMemory` implementation for games and notifications (later `*Database`), and `EvaluationDaoFile` and `CardArtDaoFile` for the evaluations and the cards' art (later buckets) | nothing above it |

`config` wires them, outside the layers. `ArchitectureTest` (ArchUnit) fails the build if a layer reaches the wrong way, or if the domain imports Spring Web, servlets or Jackson. Services, mappers and adapters take their collaborators through their constructors, so a test can wire a whole instance by hand (`testing.TestInstance`).

## Vocabulary

| Word | What it is | Type |
|---|---|---|
| Session | Everything about one game, saved between two messages: seed, seats, state, logs, outbox, version | `domain.bo.game.GameSession` |
| Seat | P1 or P2 and who sits there: a human (token hash), a bot (name + generator state), or an open seat (join code hash) | `domain.bo.game.Seat` |
| Version | +1 at every save of the session: each applied action, and the join of a human game | `GameSession.version` |
| Snapshot | What one seat may see of a state: the engine's `PlayerView`, plus what each card of its hand costs (cost auras read both boards) and the prompt and labels of its own decision | `domain.bo.game.SeatSnapshot` |
| Outbox | Each human seat's `SeatUpdate` (snapshot + redacted events) for the last 50 versions, saved with the session | `domain.bo.game.Outbox` |
| Notification | "game X is at version n", nothing more | `GameNotificationPort.publish` |
| Socket | One seat's live WebSocket on this instance | `controller.ws.SeatSocket` |
| `state` / `update` / `rejected` | Full view + whole history / view after one save + its events / to the sender only | `controller.ws.message.ServerMessage` |

## The model in six points

1. **No instance owns a game** (spec §13.4). Cloud Run may route two messages of one game, or the two players, to different instances. So every change loads the session through `GameSessionPort`, applies it, and saves it with `save(session, expectedVersion)`, an optimistic lock that answers false when another instance moved first: reload and start again; the request usually ends as `stale_decision`.
2. **Every change ends in `GameSaver`**: each human seat's `SeatUpdate` goes to the outbox (the prompt and labels are written now, since the describers read the full state), the session is saved, then `GameNotificationPort.publish(game, version)`. Notifications carry no data: each instance holding a socket to the game asks `SeatUpdateService.since(game, seat, sent)` for what that socket has not received, and sends it in order. A lost notification costs nothing; a socket more than 50 versions behind gets the `state`.
3. **The client is never trusted.** `GamePlayService.act(game, seat, decisionId, index)` recomputes the decision from the saved state, then checks, in order: game started, not over, `decisionId` current (else `stale_decision`), seat is the decider (else `not_your_decision`), index in range (else `invalid_action`). The client sends an index; it never builds an action.
4. **Bots are rebuilt at every move** by `BotTurnService`: `BotRoster` (built with the `GameEngine`, for bots that look ahead; `random` first, the client's default, then `greedy`) makes a `Bot` from its name and `rngState` with `rebuild(seat)`, it picks from its own `PlayerView`, and its new generator state is saved with the move. One save and one update per bot move. A bot's first state comes from the game seed, so a bot game replays from its setup and the human's actions. Whoever opens a socket to a game left on a bot's decision resumes the loop.
5. **One socket per seat.** A new socket is announced (`GameNotificationPort.announce`); whichever instance holds an older one for that seat gets `GameWatcher.seatTaken` and closes it with 4409.
6. **Nothing about a game lives in an instance's memory.** `GameSocketRegistry` holds only this instance's sockets and, per socket, the last version sent. `GameLocks` (striped, per game) only avoids pointless conflicts inside one instance; correctness comes from the versioned save.

## The wire format, in short

- **Views** are domain business objects built from the engine's `PlayerView` and the snapshot's texts (`domain.mappers.view`). They carry no JSON annotation: `controller.mappers.ws.ProtocolJson` says, with mix-ins, that empty optionals are written as `null`, that `ActionView`, `TargetView` and `EventTargetView` only carry their own fields, and that an event's fields sit beside its type.
- **Events** are one to one with the engine's records (`EventViewMapper`, which redacts first): `type` is the record name in snake_case, then `rules`, `text` (`EventDescriber`, from the seat's point of view), then the record's components. A new engine event needs no change.
- **Secrets**: seat tokens and join codes are 32 random bytes in base64url, stored as SHA-256 hashes, compared in constant time (`SeatTokens`). The seed is never returned.
- **REST** bodies leave optional fields out; errors are Problem Details (`ApiExceptionHandler` maps each `GameException`). `GET /api/cards` carries each card's `text` from core's `CardTextRenderer`, through `ContentService`, and its `art`, the address to download its image from.
- **Card art** lives in an art store behind `CardArtPort` (`CardArtService` → `CardArtPort` ← `CardArtAdapter` → `CardArtDao`). Today the store is a folder, `CardArtDaoFile`, one `<card id>.webp` per card (`shardbound.art-dir`, by default the repository's `assets/art/web`, `/app/art` in the image), which `scripts/publish-card-art.py` writes from the paintings in `assets/art/cards/`. A browser cannot read a folder, so the adapter hands out the server's own address, `/api/cards/{id}/art?v=<version>`, and `CardArtController` sends the image: `Cache-Control: immutable` at the current version, `no-cache` and its `ETag` otherwise, `404` for a card without art (`ContentException.UnknownArt`). Online, a bucket's DAO gives its own addresses and the server stops sending images; nothing else changes.
- **Evaluations** are the Arbiter's (phase 3), for the benchmark explorer: `GET /api/evaluations/{version}/{split}` lists a split's timestamps, oldest first, and `GET /api/evaluations/{version}/{split}/{timestamp}` returns one evaluation, served as written, since its format belongs to `ai/rag/evaluation/evaluation_json.py`; one that never ran is a 404 (`EvaluationException`). `EvaluationDaoFile` reads `<version>/<split>/<timestamp>.json` from the reports folder at each request, so an evaluation saved while the server runs is served at once; a name from the URL is only compared with the files found, never made into a path (`shardbound.reports-dir`, by default the repository's `evals/reports`; `/app/reports` in the image); online, a bucket implements `EvaluationDao` and nothing above it changes. `GET /api/datasets/{version}/{split}` serves the dataset split those evaluations score, `dataset-<split>.jsonl` as written (`application/x-ndjson`, one question per line), so the explorer shows each question's wording and answer key; it is built the same way (`DatasetController` → `DatasetService` → `DatasetPort` ← `DatasetAdapter` → `DatasetDaoFile`, `shardbound.datasets-dir`, by default `evals/datasets`, `/app/datasets` in the image), and a split never built is a 404 (`EvaluationException.UnknownDataset`).

## The client, in short

- `GameSocketService` (one per game page) holds the connection (RxJS `webSocket()`) and exposes `view`, `log`, `rejection` and `status` as signals. It applies `update`s in version order, one every 400 ms so a bot's turn can be followed (the server keeps `step-delay` at 0). A version gap clears the queue and sends `sync`. A dropped connection reconnects with a backoff, and the `state` the server sends on connection resyncs it. Close code 4409 stops it for good.
- `DecisionGroups` turns the decision's actions into clicks: sources (the card played, the attacker, the interceptor) are highlighted; selecting one lights up its targets and shows its target-less actions as buttons; a target click sends the action if only one matches, otherwise the matches become buttons (with and without Overcharge, one per sacrifice). A `choose_cards` action naming one card or unit is clicked on it (`locateIn` finds it in the view); combinations stay buttons.
- Card texts come from `GET /api/cards` (`CardBook.text`), one line per entry with its kind: a hand card shows the start of its rules (four lines) and an inspected card every line; a unit on the board is a token (`arena/unit-token.ts`: art, name, attacks, defense, states, modifiers), its text one hover or long press away.
- Card art: `CardArt.source` gives the address `GET /api/cards` sent, nothing until the cards are loaded, and a placeholder drawn from the card's id (`procedural-art.ts`) for a card without art or an image that fails. A card's art fills its face: the name sits on its top edge, the rules on a panel over its foot.
- The hand (`arena/board.html`, `board-hand.css`): each card is a slot (`button.hand-card`, the anchor the stage moves with GSAP) holding a pose (`.pose`, which CSS fans and lifts). Never put a CSS `rotate`, `translate` or `scale` on an element GSAP animates: GSAP folds them into its `transform` and leaves `rotate: none` inline, so the card keeps a stale angle and leans more at every update. A card under the mouse, under a finger held on the hand, or focused from the keyboard is read: its big copy (`.peek`, the card in `inspect` mode) stands right above the hand, over the board, never over another hand card, and its own place fades. A finger sliding along the hand reads the card under it; pulling a card up out of the hand starts the drag that plays it; so a long press inspects the other pieces, not hand cards. Nothing is read while the player aims (`focus`).
- The inspected card (`cards/inspect-panel.ts`, opened by `Inspect.open`: a click on a card that is not an action, a right click, a long press, the battle line's card thumb) is a full-screen showcase in 3D: the card spins in over the blurred page with its faction's glow, leans toward the pointer (or the phone, when the gyroscope setting is on), and a drag turns it to its back; `ShowcaseMotion` is its spring, `CardComponent.pose` the angle, and the card then catches a glare and a foil. Escape, the close button or a click beside it closes it. The board's hover preview of a unit stays a flat card.
- The battle line (`arena/intent-bar.ts`, filled by `GamePage.intent`) is the one place that says what is happening: the engine's prompt when nothing is selected, the selection in progress (with the card's text or the attack's damage and cost), the engine's label of the action a hovered target would pick, the action buttons and End turn; during a resolution, the text of each event. While the player aims, everything that is neither a target nor the selection dims.
- Attack previews (`arena/combat.ts`) are display only: `projectAttack` sets the engine's `AttackView.damage` against each target's defense or HP and names the outcome (`hit`, `lethal`, `anchored` for 11.3.4, `linked` for 11.5.2, `effect` without damage); the server still decides, and the defender may intercept. Under attack, `pendingCombat` (from the last `attack_declared`) projects the strike on the threatened unit and on every unit that can intercept.
- The Chronicle (`game/game-log.ts`) groups the events by turn and links each rule ID to its section of the rulebook on GitHub (`game/rulebook.ts`, one entry per rulebook file).
- `arena/stage/` plays each event over the board the player still sees, then lets the new board slide in. Skip and the speed setting apply to all of it.
- Motion: every animation respects reduced motion and the instant setting, and GSAP animations stop when their component is destroyed. The home's Three.js scene runs only on a fine pointer above 800px and stops at rest or when hidden; the page works without WebGL.
- The collection (`/cards`, `collection/`) shows every card from `GET /api/cards` and `GET /api/decks`: a search on the name and the rules text, filters by faction, type and deck, grouped by faction, deck (with each card's copies), cost or type, ordered by cost or name. `collection.ts` holds the logic as pure functions; the view lives in the URL. When the view changes, the cards slide to their new places with a view transition (not when grouped by deck, where a card shows once per deck). A card opens in the 3D showcase.
- The lab (`/lab`) only shows recorded evaluations (`/api/evaluations/`, with the questions from `/api/datasets/`). It never runs a model and never estimates a score for a combination that was not run. The random retriever is a separate floor, and the selection lives in the URL. The leaderboard (`lab/leaderboard.ts`, the first tab) leads with the best pipeline by the ranking metric, then ranks them all, showing at a glance the scores `LEAD_METRICS` names (`lab/metrics.ts`) and the one it ranks by. The leaderboard, each dot plot of the Metrics tab and the recall curve's readout show ten pipelines at a time (`lab/pages.ts`, `Pager`), and a ranking that changes under an open page moves its rows (`RowMotion`): a row the new order moves glides to its place, and a row that crosses the page's edge leaves or comes in through it. The builder (`lab/pipeline-builder.ts`, tab `builder`) draws the pipeline left to right, each step with every variant it was evaluated with (`lab/builder-model.ts`; BM25's settings are one family), and shows the score of the exact matching run as soon as a step changes, each choice saying how Recall@10 would move; a combination never run says so. Every metric's name, format and texts come from the evaluation's `metrics` block through `lab/metric-catalog.ts` (`MetricCatalog`, which every view that shows a metric takes as its `catalog` input): its display says that a count is context and never ranks, that a time is better lower, and that a share or a score runs from 0 to 1. Every bar is longer for a better value (`ceiling`, `barLength`: a time's bar is reversed), and the history chart flips its axis for a time and draws a time per device, since it depends on the machine (each evaluation says where its models ran, `deviceName`; a file without a device ran on the CPU). A file written before that block keeps only the names the catalog knows. The Metrics tab (`lab/metrics-graph.ts`) opens on the recall curve, "How much context is enough?" (`lab/recall-chart.ts`, which lights the curves of the page its readout shows), then one dot plot per score; each section folds on itself. The "Our metrics" page (`lab/metric-guide.ts`, tab `guide`) shows every described score, grouped by role, with its value for the top pipeline by Recall@10 and the random floor; the counts and the curve are left out. Rows, markers and values in the lab move on springs (`lab/springs.ts`: each spring is a GSAP ease and the same curve as a CSS `linear()`, which the lab page sets as `--spring-*` properties). A number that changes counts to its new value, or rolls the characters that change when its unit changes, and flashes green or red when it got better or worse (`RollingNumber`); a leave animation ends on a timer too, for a tab that draws no frame. A new pipeline step or variant needs one entry in `lab/pipeline-model.ts` (`PIPELINE_STAGES`) to be drawn in a question's pipeline flow, which widens with its columns and scrolls past the screen's width; a variant shown at a glance also needs its name in `presentation.ts` and its description in the builder (`builder-model.ts`); a new step, its name (`LAYER_NAMES`, `presentation.ts`) and its role (`ROLES`, `builder-model.ts`). A new score shows everywhere by itself; to be a column of the leaderboard, it needs its key in `LEAD_METRICS`.
- `public/portals/` holds the home's generated landscapes, with their exact prompts (`prompts.json`) and one provenance file per image (`*.webp.json`).
- Cold starts: the server runs on Cloud Run with no instance kept warm. `core/server-wake.ts` times every `/api/` request made with `HttpClient` (the `watchServerWake` interceptor; card images load through `<img>` and are not timed) and the game socket's first connection. When waits stay in flight for more than 3 s, counted from the first, `ServerWakeBanner` shows at the top of every page with the seconds waited, then "The server is up" when one is answered. A 5xx or no answer at all is not an answer: once no wait is left, the message just goes away.
- Tokens live in `localStorage` (`shardbound.game.<id>.token`), so a reload resumes the game. Two seats on one machine need two browsers, a private window, or a second dev server (`npm start -- --port 4201`).

## Changing it

Read `references/recipes.md` for step-by-step changes: a REST endpoint, a view or event field, a protocol message, a bot, a new DAO, a client screen. `references/flows.md` follows one click through the layers, a game between two instances, and a reconnection.

Rules of the house, on top of the engine skills' code style:

- **Put code in its layer.** An endpoint, a DTO or a message: `controller`. A rule of hosting a game (who may answer, what a seat may see, when to save): `domain`. How a port is implemented, entity mapping: `adapter`. A map, a SQL query, a pub/sub call: `dao`. The controller never calls an adapter or a DAO.
- **The server translates, it never computes a rule.** If a client needs a number or a sentence the engine does not give, add it to core (a describer, a function next to `Costs`).
- **Talk to a seat only through its view and redacted events.** Mappers take what the engine lets the seat see.
- **Every change of a session goes through `GameSaver`.** Never send to a socket from a service; the outbox and the notification do it.

## Running and debugging

```bash
cd engine && ./mvnw -pl api -am spring-boot:run   # http://localhost:8080; one log line per applied action
cd frontend && npm start                          # http://localhost:4200, proxies /api and /ws
```

- Each applied action logs `game=… seat=… decision=… action="…" version=… instance=…` (`GameSaver`). Tests silence it in `logback-test.xml`.
- A client stuck on an old view: compare its `view.version` with the session's; a gap should have sent `sync`.
- A `rejected` you did not expect: the reason says which check failed (point 3 above).
- `BotTurnService.MAX_BOT_MOVES` (10,000 in a row) fails loudly if a bot loop never gives the decision back.

### Play-testing in the browser pane

To check a change in the real client, run `docker compose up --build` from the root (it replaces a stack already running) and open http://localhost:4200 in the browser pane.

- **A seeded game**: from the page, `fetch('/api/games', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ deck, opponent: { type: 'bot', bot, deck: botDeck }, seed }) })`, store `playerToken` under `shardbound.game.<gameId>.token` in `localStorage`, then go to `/games/<gameId>`. The creator is P1, and P1's draws depend only on the seed: to pick a seed with a good opening, print P1's hand and the top of its deck after `newGame` for a range of seeds in a throwaway core test.
- **The page**: every clickable element carries its key in `data-key` (`card:3` in the hand as `button.hand-card`, `unit:61` as `button.unit`, `player:opponent` as the HUD's `button.vitals`, `relic:5`) and its state in `data-mark` (`selectable`, `selected`, `targetable`; on the unit token, the hand card or the vitals button); the decision's actions are buttons of `app-intent-bar`, labelled by the engine (`End your turn`, `Play … overcharged (…)`, `Don't intercept`…), and `.cancel` drops a selection. A selected attack writes its outcome in each target's `.projection`. `get_page_text` reads the board, the battle line (`app-intent-bar .title`, which narrates each event while the stage plays) and the Chronicle.
- **Clicking**: while the pane is hidden, mouse clicks do not land; click through the DOM (`element.click()`) with `javascript_tool`. Updates arrive one every 400 ms, so wait a second or more after each action, longer for a bot's turn. A `javascript_tool` call times out after 45 s: drive long sequences in several calls.
- **Choices without a button**: a target asked in the middle of a resolution, such as the target of your unit's echo during the bot's turn (11.1.3), shows only `targetable` elements and no action button: click one. A script that drives your side must handle it, or it waits forever.
- **A whole game**: define helpers on `window` in one call (click a button by its label, list the enabled buttons, play your turn with a simple policy, wait until `End your turn` has been enabled for about a second, declining intercepts: it is absent while the stage plays), then play one round per call. A game against `greedy` lasts 30 to 40 turns.
