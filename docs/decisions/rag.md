# RAG decisions

Why the RAG Arbiter is built the way it is, step by step, and what was tried or rejected. The design (`docs/design.md` §5.2, §6.2, §6.3) says what the pipeline is; this file keeps the reasons. Each decision was taken with the maintainer. A new one goes at the end of its step.

## How it is measured

- **A question's relevant chunks are its citations.** The answer key already says what a correct answer must cite, so nothing is labelled by hand.
- **Recall@10 decides, MRR explains** (2026-10-12). A chunk that is not retrieved cannot be used, and the prompt holds 10. Replaced on 2026-11-12 by context recall, which is Recall@10 for a ranking (below, after step 9).
- **The prompt holds 10 chunks** (2026-10-12). A chunk is about 40 tokens and no question needs more than 10 rules; 5 would cap 8% of the questions. 5 and 20 are variants. Since step 8, the cards the question names join them.
- **A recall curve, not a composite score** (2026-10-17). To show that the refs expansion does better with fewer chunks, runs are compared at the same number of chunks. A score weighing recall against size was rejected: arbitrary weights could change the winner (design §6.3).
- **No candidate recall** (2026-10-17). It always equalled the curve's last value, and was 100% for every retriever that returns the whole corpus.
- **One file per evaluation, and no index file.** A file is never overwritten; an index would be one more thing to keep in sync, and the frontend reads the timestamps. Each run is named by its layers, so that the frontend switches between runs by layer.
- **Every evaluation says why it was run** (2026-10-17), so that the benchmark explorer can show it.
- **CI compares a pull request with main only** (2026-10-26). It used to compare its run with the evaluation the pull request itself committed, which every pull request touching retrieval did, so it never saw a drop against main. It now evaluates the baseline on the CPU and compares it with the evaluation main records; a run that lost more than 2 points of Recall@10 fails a check that is not required, a drop the maintainer may accept. Since 2026-11-12, of context recall, in a check renamed "Context recall against main" (below, after step 9). One dev question moves a score by about 1.6 points, so a drop of 2 is more than one question.
- **The baseline is named once in code** (2026-10-26), `ai/rag/baseline.py`: MiniLM-L6 after RRF and the refs. It is the pipeline the Arbiter would serve, so it must run on the CPU, which CI and Cloud Run have: Qwen3-Reranker ties it at 10 and would take hours there.
- **A pull request that changes what retrieval depends on commits an evaluation of its own code** (2026-10-26), a required check: recorded at a clean commit whose files retrieval depends on are those the pull request has, with a run of the baseline, from a branch up to date with main. So main always records an evaluation of its own code. The files are listed by path, a little wider than needed: a change to the engine's bots calls for an evaluation too.
- **A new report format replaces the old reports** (2026-10-18). The first report of the reranker's format replaced every older one rather than converting them.
- **Binary nDCG@10 and @20 explain too** (2026-10-22), at the same cutoffs as Recall. Agreed on 2026-10-17 for after the reranker, it is computed on every run, like MRR, so it also shows what the reranker adds: on v2 dev, the binary nDCG@10 of the fusion with the refs is 0.550 without the reranker and 0.623 with it. Every cited chunk gains 1: the context rules are full citations, so no chunk weighs more than another. It shows what Recall@10 hides: a cited chunk at rank 10 counts as much as one at rank 1 for Recall@10, but 0.29 for nDCG. A graded nDCG would sit next to it under its own name.
- **Each metric is a class that describes itself** (2026-10-22). It scores one question from the ranks of its cited chunks, and says what it does, how and what it represents; the evaluation loops over the list of metrics, and every evaluation file keeps the descriptions, which the benchmark explorer shows. One interface only: the values that are not a metric's mean (the count, the candidates, the recall curve, the latency) are computed by `score_group` and only described.

## Step 1: the chunks

- **Java writes the chunks.** The rulebook parser and the card text (`CardTextRenderer`) are in the engine.
- **A rule's prefix is the titles of its sections, without its ID; cards and terms get none** (2026-10-12). No question quotes a rule number, and the prompt's tags carry it.
- **A section number stands for all its rules** (2026-10-12): the "(7)" of rule 5.3.1 brings the combat rules.
- **A chunk carries its name** (2026-10-17), written by Java (a card's or a term's), not parsed from its text.
- **The database is the RAG's only source of chunks** (2026-10-14). Every retriever of an evaluation is built from the indexed chunks, so a forgotten index cannot mix two versions of the corpus in one run. `ai/.corpus/chunks.jsonl` is only what the index reads.

## Step 3: BM25

- **bm25s and PyStemmer, rather than a hand-written BM25** (2026-10-12).
- **The baseline keeps stop words.** bm25s removes English stop words by default, but "not" and "no" carry meaning in rules.
- What it showed on dev: BM25 finds the factual questions (100% Recall@20) and the simple-rule ones (92%). It misses the scenario questions, which name cards rather than the rules they need, and the deck questions, whose decklist floods the ranking and which never say "30". Its five formulas and its stemming and stop-word variants are within about two questions of each other.

## Step 4: dense retrieval

- **Qwen3-Embedding-0.6B on CPU is the baseline** (2026-10-14), one entry of a registry of local models: another model is one more entry.
- **SQLAlchemy, no SQL in strings.**
- **No migrations yet.** The tables are created from the entities, so a schema change means an empty database and every chunk embedded again. Alembic comes when data must survive a change.
- What it showed: dense retrieval finds the deck questions by meaning (92% Recall@20, BM25 0%) and every simple-rule and factual question, but misses the multi-step ones (3%, BM25 36%). The two complement each other, which is the case for fusion.

## Step 5: RRF fusion

- **One fusion only** (2026-10-16). The BM25 variants are within two questions of each other on dev, so a fusion per variant would measure noise. A fusion variant changes one of its own settings.
- **The card names moved to step 6** (2026-10-16). A card chunk is not a citation of a scenario question, so adding it cannot raise recall before its refs are followed.
- What it showed: Recall@20 78.6% (dense alone 74.1%), Recall@10 59.6% (dense 62.3%). A chunk that only one retriever ranks well sinks under chunks both rank fairly: rule 8.3, 2nd for dense retrieval and 67th for BM25, comes 17th.

## Step 6: card names and the refs expansion

- **Card names are matched exactly, as whole words, on the lowercased question, with no typo handling** (2026-10-17). A tolerant layer (edit distance, an LLM) becomes a variant once questions with typos can measure it. Plurals ("two Sprouts") are not matched either. Matching while ignoring case was dropped after a review: a letter such as "ſ" matches a name that it cannot then be looked up by.
- **Vocabulary terms are never matched**: "destroy" and "die" are in most questions.
- **The refs are attached before the reranker** (2026-10-12), so a chunk found only through a ref is judged like the others.
- **And not again after it** (2026-10-23). The reranker has already ranked them among the candidates, and the prompt keeps its 10 chunks. The variant asked on 2026-10-17 was dropped by the maintainer without being measured. Reversed on 2026-11-12 for the named cards' refs, as a variant of the context (below, after step 9).
- What it showed: 95.3% of the relevant chunks among 41.3 candidates on average, against 78.6% in the fused top 20; interaction questions from 0% to 89.8%, multi-step ones from 24% to 73.1%.

## Step 7: the reranker

- **The reranker is a step of its own, not a retriever** (2026-10-18). Several rerankers will be tried, and the explorer must build a pipeline with or without each one.
- **One class per reranker, which loads its own model** (2026-10-18). A model class beside the reranker class made two classes that rank.
- **The pipeline is steps, and the evaluation is the tree of every pipeline they make** (2026-10-18), each node computed once and knowing its parent. Rejected first: a retriever computed again for each reranker, a cache inside the retriever, and a ranking handed back to the retriever to cut.
- **A reranker reads the candidates, never the corpus** (2026-10-18, as design §5.2 says). A retriever hands on its top 20, the expansion its whole list.
- **MiniLM-L6 comes first** (2026-10-18): 22M parameters, the classic small baseline. Qwen3-Reranker-0.6B and Jev *noul* come later.
- **Qwen3-Reranker-0.6B is the second reranker** (2026-10-23): a cross-encoder built on a 0.6B LLM, whose score is the logit of "yes" minus the logit of "no". It loads from its official repository with sentence-transformers, like MiniLM, so both extend one `CrossEncoderReranker`; its revision is pinned, since the repository was changed after release to load that way. It is told the task by one generic instruction, "Given a question about a card game's rules, retrieve the rules and cards needed to answer it.", in place of its default one about web search.
- **The rerankers load their models in float32** (2026-10-25). Qwen3-Reranker's weights are stored in bfloat16, which keeps about 3 significant digits: on the same CPU, the batch size alone moved its scores by about 0.07, enough to swap close candidates. In float32, the CPU and a GPU ranked 6 dev questions identically (scores within 0.0001), whatever the batch size. It costs speed on the CPU: in one-off timings, Qwen3-Reranker took about 50 s a question instead of 17 s.
- **The embedding model loads in float32 too** (2026-10-25). Qwen3-Embedding's weights are stored in bfloat16 too: the first evaluation on the GPU embedded the questions with AMD's build of torch, the chunks having been embedded with the locked one, and cosines moved by up to 0.006. Recall@10 did not move, but the dense retriever's top 20 stayed the same for 18 dev questions out of 61 only. In float32, two builds give cosines within 0.000001; the index was embedded again. The vectors are kept under the model's name and format (`qwen3-0.6b/float32`), so that an index embedded in another format is never reused: a change of format embeds every chunk again by itself. On the CPU of AMD's build, float32 is slow (2.7 s a question), so the embedding model runs on `RAG_DEVICE` too.
- **Every model's revision is pinned** (2026-10-26): Qwen3-Embedding and MiniLM-L6 as Qwen3-Reranker. Qwen3-Reranker's repository changed after its release, and a model's configuration on Hugging Face (its query instruction, say) changes its vectors and scores: a later change must not move a recorded evaluation.
- **A GPU through `RAG_DEVICE`, the CPU by default** (2026-10-25). On the maintainer's RX 6800 XT, with AMD's ROCm build of torch, the main pipeline takes 0.11 s a question with MiniLM-L6 and 1.15 s with Qwen3-Reranker (p50 of the evaluation of 2026-10-25), against 0.72 s with MiniLM-L6 on the CPU (2026-10-22), with the CPU's rankings on 6 dev questions. A one-off timing of Qwen3-Reranker alone, in float32 on the CPU, gave about 50 s a question. CI and other machines stay on the CPU. The GPU build of torch lives in a second environment, `ai/.venv-gpu`, beside the locked one, so that a plain `uv run` (the test hook's) never replaces it under a running evaluation; a uv extra for it would need the lock re-resolved and tried first. Each evaluation records its device and torch build, since latency depends on them and the commit alone does not say which torch ran.
- What it showed (2026-10-25, every model in float32, on the GPU): the whole pipeline puts 71.1% of the cited chunks in the prompt's 10 with MiniLM-L6 and 70.7% with Qwen3-Reranker, a tie, since a question is worth 1.6 points: MiniLM-L6 stays the baseline. Qwen3-Reranker puts 86.7% in its 20 (MiniLM-L6 81.3%) and ranks above MiniLM-L6 at 10 after 16 of the 20 candidate lists, mostly the weaker ones (dense retrieval, BM25), but finds the first cited chunk later (MRR 0.620 against 0.661) and takes ten times as long (1.15 s a question on the GPU, against 0.11 s). It brings rule 8.2 (Destroy) into the 10 when a question never says "destroy" (Tempest, Shardbreak Pulse), and sinks rule 9.11, the order in which an action and its triggers resolve, from 1st to 11th. The 72.7% of 2026-10-22 was one question luckier: with the index in bfloat16, rule 2.1 came 20th in the dense ranking of a deck question; in float32 it comes 21st, out of the top 20 the reranker reads.

## Step 8: the context and the answer

- **The RAG chooses the context, not the Arbiter** (2026-11-07, the maintainer). Handing the Arbiter its chunks is the RAG's job, and the prompt's size is already a variant of the RAG (design §6.2). `rag/pipeline.py` runs the techniques a run's layers name, the context last (`rag/contexts/`, a step of its own since 2026-11-12).
- **The context is the reranker's 10 chunks, then the cards the question names that the reranker ranked past them** (2026-11-07). The named cards joined the candidates since step 6, but the reranker could rank them past the cut: on v2 dev, 6 of the 15 scenario questions lost a card they name (Tempest came 11th in the question about Ash Warden, Roaring Pyre and Tempest). A card is about 40 tokens. The retrieval metrics still score the ranking, so they do not move; the context is judged with the answers (and scored by context recall since 2026-11-12, below).
- **Answering and evaluating the answer are separate packages** (2026-11-07, the maintainer): `arbiter/generation/` answers, `arbiter/evaluation/` checks the answers, and nothing but the evaluation imports it, which a test checks. The Arbiter a player talks to carries no evaluation code, and generation reads no RAG type, so that a configuration without RAG answers too.
- **Claude Haiku 5.5 answers first** (2026-11-07, the maintainer): the `api+rag` configuration, the reference ceiling (design §6.2). Structured outputs hold its reply to the schema, which Pydantic validates once more; a reply that is no answer gets one more attempt, and both are counted. Its effort is set to medium, the API's default for the model, written down so that it does not move with the default *(proposed)*. The key is read from `CLAUDE_KEY`.
- **Every completion is kept on disk** (2026-11-07), by the generator's settings (the answer's schema among them, since the model reads its field descriptions), the prompt and the attempt: a rerun costs nothing and reads the same answers.
- **Claude runs at its default temperature** (2026-11-07). Haiku 5.5 takes no sampling setting, so each question gets one sample, which the cache keeps. How much a dev score moves between two uncached runs is to be measured with the answers *(proposed)*.
- **The key-fact extractor has Luna 6 as baseline and Jev as a variant** (2026-11-07, the maintainer), for step 10: both behind one interface that reads one fact in one answer, compared on answers the maintainer labels by hand, on their errors, cost and latency. A configuration where Jev reranks or abstains is graded by Luna 6 only.

## Step 9: the answers checked by code

- **Six answer metrics, scored by code with no model** (2026-11-07, the maintainer): valid answers, answered, correct refusals, citation recall, citation precision and step order, one class each in `arbiter/evaluation/answer_metrics.py`, like the retrieval metrics. Each gives an answer a value from 0 to 1, or None when it does not apply, which the mean of a group leaves out, saying how many questions each metric scored. The key facts come at step 10, with the extractor.
- **Every answer metric describes itself** (2026-11-07, the maintainer): what it does, how it is computed and what it represents, kept in the evaluation's file with every other value of a group, so that the benchmark explorer shows them as it shows the retrieval's. A test fails on a value of a group's scores with no description. The cost has its own display, `dollars`, which the client writes and ranks lower-is-better.
- **Precision tolerates a rule the trace carries and a card the question names, counting them neither right nor wrong** (2026-11-08, the maintainer, after the audit). The prompt asks for the rules and cards an answer relies on; design §6.3 tolerated the trace's other rules (a spell going to the graveyard) and spoke of rules only. Counted right, they gave an answer citing only the question's cards 100%: on v2 dev, the interaction answers scored 100% precision at 0% recall. So precision is the right ids over the right and the wrong ones, and an answer citing only tolerated ids is not scored. The cards are those the question names, found as the RAG finds them: the dataset's `cards` holds every card of a scenario, the opponent's hidden ones and the fillers included. A rule the key does not list stays wrong, even one that supports the answer (6.8 for a card's cost): precision reads the key's essential rules as the only right ones.
- **Abstention is two metrics** (2026-11-08, the maintainer, after the audit): answered, on the questions that have an answer, and correct refusals, on those that have none. One mean over every question was mostly the first: with 61 answerable questions of 72, a model that never refuses scored 84.7%. Each is a share where higher is better, so the false refusals are written as their complement, answered.
- **A scenario's steps come from the engine** (2026-11-07): `rules` lists the key events' rules in the order they happen, and two rules next to each other are one step when an event of the trace carries both, like Echo's 11.1.1 and 11.1.2. Only scenarios have steps: a deck's problems have no order.
- **Step order counts pairs** (2026-11-07, the maintainer): of the cited rules from two steps, the share of pairs cited in order, so that one rule out of place costs a few pairs, not the whole score.
- **The answers' evaluations go to `evals/answers/`** (2026-11-07, the maintainer), shaped like a retrieval evaluation. `evals/reports/` is what the RAG's gate and the lab read: an answers' file there would fail the gate, which wants a run of the baseline in the newest report a pull request adds.
- **The evaluation has its own command**, `python -m arbiter.evaluation` (2026-11-07), since nothing of the Arbiter imports its evaluation.
- **Each answer keeps the time its call took and its cost** (2026-11-07, the maintainer). The generator measures the call and the cache keeps it, so a rerun reports the first call's latency, not zero. The cost is the tokens at the model's list price per million, which the generator declares: $0.10 in and $0.50 out for Haiku 5.5 (October 2026). The RAG's latency stays in its own report.

## After step 9: the context as a step

- **The context is a step of the RAG, with its contract and registry** (2026-11-12, the maintainer): `Step.CONTEXT`, `ContextBuilder`, `rag/contexts/`. A run's layers name it under `context`, after `rerank`, so the lab, `rag compare` and the gate read it like any layer. The baseline names its context too, since it is the pipeline the Arbiter answers with.
- **A variant adds the refs of the cards the question names, one level deep** (2026-11-12): `top10-plus-named-cards-refs`, beside today's `top10-plus-named-cards`. The refs join the candidates before the reranker, but it ranks them low: the question about Ash Warden, Roaring Pyre and Tempest shares no word with rule 8.5 (Modify), which came 44th of 50. The cut at 10 dropped all 7 rules the question cites; the variant brings 6 back.
- **The refs of the named cards only, not those of the top 10's other cards** (2026-11-12, the maintainer). On v2 dev, following them too gave 86.0% of the cited chunks against 84.9%, for 23.0 chunks against 19.7: an offline computation, on the rankings of `evals/reports/v2/dev/2026-11-07T23-27-39Z.json` and the refs of the chunks built that day, since no code keeps that variant and no evaluation records it. The 1.1 points were 2 questions about Coral Font, gained by luck: Ash Warden and Spring Tide, which those questions do not name, were in the top 10 and refer to rule 8.5. Coral Font's own refs do not hold 8.5: a ref to fix in the corpus, not a rule of the context.
- **The refs come card by card, in the order the question names the cards, each card's refs in the card's order** (2026-11-12, the maintainer). A keyword's rules stay together, 11.1.1 to 11.1.11 for Echo, and the context does not depend on an expander being in the pipeline. The reranker's order was the other choice.
- **Context recall is the decision metric** (2026-11-12, the maintainer): the share of a question's cited chunks the prompt would hold, on the answerable questions, each weighing the same. A run that ends with a ranking would hand the prompt its first 10 chunks (`PROMPT_SIZE`), so there it is Recall@10, and no ranking's score moves; a run that ends with a context hands it every chunk of it. It replaces Recall@10 in the lab and the gate, so that one number ranks every run. Recall@10 cannot tell two contexts apart, since both keep the same first 10. Between rankings, every prompt holds 10 chunks; a context holds more and wins by its size alone, so its recall is read with its number of chunks, and the dev answers choose the context. A prompt of 20 chunks, later, would move `PROMPT_SIZE`. The definition was written after a first look at its dev value (71.1% and 84.9%), not before as planned; it is Recall@10 for a ranking and Recall@k with the cutoff taken out for a context, so no parameter was fitted; but the metric was chosen knowing that it separates the two contexts where Recall@10 ties them.
- **A context run keeps context recall, Recall@10 and nDCG@10, its chunks and its latency** (2026-11-12, the maintainer). Recall@10 and nDCG@10 are those of the ranking it cuts when that ranking holds 10 chunks or more, since the context keeps the same first 10; a BM25 variant can hand on fewer, and the named cards then come within the first 10. Recall@20, nDCG@20, MRR and the recall curve are left out: they would read the context's order past the 10th chunk, which no step reads, and a context of 12 chunks scored 71.1% at Recall@20 against its reranker's 81.3%. A context run keeps every chunk of it, where a ranking keeps its first 20, so that the lab draws the whole prompt and `rag compare` sees a change past the 20th.
- **`rag compare` and the gate read context recall** (2026-11-12, the maintainer), and the number of chunks beside it, without gating on it. Against an evaluation recorded before context recall, they read Recall@10, the same value for a ranking. The check is renamed "Context recall against main". The lab gives a file recorded before it its Recall@10 as context recall, so that every file ranks by the same metric.
- **The full grid: every pipeline, with and without each context** (2026-11-12, the maintainer). 60 runs become 180, so that the explorer builds any pipeline with any context.
- **The answers' evaluation answers from every context** (2026-11-12): one run per context and generator, on the baseline's ranking, whose techniques are built once.
- **Which context the Arbiter serves is not decided yet** (2026-11-12, the maintainer): `top10-plus-named-cards` stays the baseline, both are recorded, and the choice is taken on the dev answers once there is more data: the key facts of step 10, or a larger dev split in a new dataset version. The test split shows both contexts and chooses nothing. Context recall alone does not choose: on v2 dev the refs double the deck questions' context (20.5 to 43.8 chunks) and gain nothing there.

## Later

- **Indexing moves behind the FastAPI service, and becomes asynchronous** (2026-10-14). Once the service exists, the engine posts its chunks, and the service answers `202 Accepted` and embeds them in the background. Not before: the engine's batch would need a running server.

## Open

- One Qwen3 model loaded once for every dense-based retriever.
- A smaller k for RRF *(proposed)*: k = 60 put rule 8.3 17th.
- A "perfect" retriever, the ceiling *(proposed, not asked for)*.
- The whole corpus in the prompt, with no retrieval (about 7,400 tokens), judged on answer metrics only (deferred, 2026-10-12).
- Questions in French: BM25 fails on them, a multilingual embedding model does not. An idea only.
- The prompt of the configurations without context (`base`, `lora-knowledge`): the one prompt says to answer from the context only, which would make them abstain. To settle before their first run.
- Rule 8.18 is referred to by no chunk, so no context holds it: 5 interaction questions of v2 dev cite it. Coral Font's refs do not hold rule 8.5, which its aura applies. Both are refs to fix in the corpus *(proposed)*.
- A context that keeps only the refs the reranker ranks high *(proposed)*: Ash Warden brings Echo's 11 rules where a question needs 3.
